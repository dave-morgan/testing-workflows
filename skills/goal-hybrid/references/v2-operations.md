# Operations for hybrid and adaptive workflows

Read alongside protocol.md and runtime.md. This file takes precedence over their generic repeating-timer suggestions and supplies the extra logging/state contract for these two workflows. The original four skill installations are unchanged.

## Runtime and roles

Use a coordinator, one implementation owner, and separate observer/reviewer contexts. All children receive the original request and amendments, relevant goal IDs, exact workspace, role authority, actor ID/log path, policy version and mode epoch. They must not recursively invoke an orchestration skill or spawn children. Preserve provider/model preferences. Codex and Claude use the portable agent adapters in runtime.md; missing concurrent observation or policy-delivery capability is a blocker, not permission to substitute self-observation.

In T3, use delegate_task for a background implementer, follow returned next, and do not poll the running delegate. Existing permitted scheduling may provide genuinely independent artifact-observation opportunities; it must not be used to poll task_status, completion or a PR. Arm an observation opportunity before yielding to the background worker. If host instructions prohibit even independent observation scheduling, report the capability blocker. Work on a child uses its bound workspace; never create a checkout in its task text. A new delegated review uses a new delegate_task, not thread_send. Live thread_send is only for an implementation policy handoff or an authorized steering instruction, never a replacement review.

Both workflows require independent observation opportunities. Default target cadence is five minutes, configurable by user, plus actual host-supported progress events. An observer pass normally inspects changed evidence and open risks; reuse prior verified evidence with its snapshot identity instead of rerunning every test. Final checks remain comprehensive. No overlapping observer passes. Record coalesced opportunities and review cost.

## Bounded observation and provider failures

Do not create an indefinitely repeating interval schedule. On a host with one-shot schedules, keep at most one future observation wakeup, rearmed only from a healthy coordinator entry after reconciling current state. A wakeup that cannot start because of a quota failure cannot rearm itself. This bounds our scheduled attempts but does not control retries the host itself performs.

For T3, when permitted, use schedule_task with bindToCurrentThread=true and schedule={type:'once',runAt:<real UTC timestamp>}. Persist its returned ID and actual nextRunAt. The prompt contains the run path, request/goal version, policy epoch, observation deadline and role restrictions. On a healthy wake, consume/delete the expired schedule and arm at most one successor after checking for completion, limits, or active observer coalescing. It is valid to arm the successor before dispatching a new review/worker, so yielding does not lose observation opportunities. Never infer that a configured deadline actually fired. A child completion can wake the coordinator independently; reconcile and retain a single future observation opportunity.

On a visible provider quota/rate-limit error: record resource_limit or transient_failure and what actually failed, checkpoint, stop/reconcile owned writers, and pause/delete any future observation schedule. Do not rearm, loop retries, or switch providers/models without authorization. Do not send more work to the failed provider to ask whether it is available. Resume on user/host re-entry after capacity is known restored, with a logged interruption gap and no duplicate writer. A one-shot wake that failed before any agent ran may only be visible in host history on resume; document it then. Do not promise automatic recovery when the host lacks it.

If a mandatory gate/final validation is unavailable, dependent work cannot be declared verified. A normal temporary observation delay is logged rather than turned into a fake pass. Work may continue only within already granted authority and owned execution resources; no claim of continuous independent supervision during an outage. Final cleanup removes the pending wakeup, coalesces queued stale events, and settles/cancels owned children.

## Logging and identity

Use scripts/runlog.py to initialize workflow goal-hybrid or goal-adaptive. Run directory must not preexist; create the request/config outside it before init. The logger is a recording tool, not a scheduler or enforcement engine. Every agent writes its own events/<unique-actor>.jsonl; the coordinator alone writes canonical goals/checkpoint/report and routing state. Require child log/evidence paths in dispatch briefs, then verify returned records exist. Missing child streams are a gap to repair with honest coordinator events, never impersonated retrospective child records.

Record configuration and available capability evidence before implementation: goal version, platform, actual model/settings, owner handles/native session IDs, policy version, current mode/epoch, cadence mechanism, risk/gate decisions, snapshot identity and user limits. Do not log secrets. Preserve request text and accepted changes separately; role changes never weaken the goal.

Every plan/gate/observer/final review and every wait/handoff has start/end events with the same span ID, author identity, snapshot/range, event relationships, and actual timestamps. Open spans remain visibly open after interruptions. On resume, append run_resumed and reconcile child/writer status before starting another. Use one effective terminal outcome per active run segment: never append duplicate completion events on report regeneration. If a stopped/resource-limited run resumes, explicitly link the prior terminal segment rather than erase history. CLI report's latest run_finished is not a substitute for this discipline.

Record role/phase cost, useful defects discovered, discarded work, steering acknowledgements, and reviewer verdicts. Collect actual exposed provider input/cache/output counters, with scope and native session ID, when available; maintain a role/session ledger so a later audit can recover totals. Count a cumulative session counter once per unique native session and distinguish inherited context occupancy from consumption. Cached input and reasoning output are subsets, not extra totals. Missing usage stays null; preserve the lookup path/host handle and explain why it is unavailable. Never search unrelated sessions or invent cost. Estimates belong in separate fields marked estimate, with basis and units; measured durations/tokens are recorded later.

## Completion

Either implementer or observer may trigger a final candidate. Receive a checkpoint acknowledgement, freeze a content-identified snapshot including relevant dirty/untracked files, and launch a fresh final validator distinct from the implementer, periodic observer, and gate/plan reviewers. Check the original goal, role/state/date boundaries, persistence and integrated user journeys using independent evidence. Treat ambiguous product policy explicitly rather than silently enlarging scope. Reviewers may report a justified limitation; they cannot redefine acceptance to obtain PASS.

FAIL reopens affected work and returns to the selected workflow; INCONCLUSIVE stays unverified. Relevant changes invalidate prior final PASS. A mode switch is never a completion result. A completed run requires a final PASS at the delivered snapshot and a complete event/usage/evidence index. Write SUMMARY.md and report.json with coverage, defects, gate/observer/steering overhead, active versus inactive time when measured, usage availability, quota behavior and remaining limits. Adaptive summaries additionally expose every proposed/accepted/rejected/reversed switch, mode dwell time, estimated versus measured transition costs and observed consequences; do not claim causal savings from intuition.
