# Goal hybrid lean plus

The main agent implements the full request directly. Separate agents review the plan, one coalesced risk boundary, a focused UI integration checkpoint, and the final result. There is no separate coordinator or implementation worker, periodic observer, observation schedule, or automatic workflow switching. Five agent contexts are the normal topology; justified re-reviews may add contexts. This is an efficiency hypothesis, not a promise of equal quality or savings.

Read [lean operations](references/lean-plus-operations.md) for logging, review briefs, runtime adapters and interruption handling. This skill is self-contained; do not load another goal skill or its observer protocols.

1. Preserve the original request and accepted amendments. Derive stable outcome IDs and observable acceptance criteria. Write a short dependency plan and explicit policies for consequential ambiguities. Select one coalesced gate for authorization/state, durable data, or integration contracts that later work will depend on. Explain the risk it prevents. For a task without such a boundary, the plan reviewer must confirm why no gate is justified; cosmetic tasks do not create gates.
2. Launch an independent plan reviewer with the original request, plan, policies and proposed gate. Ask for missing coverage, policy errors and unnecessary gates, not a second implementation plan. Resolve blocking findings and obtain PASS before implementation. Plan approval is not runtime verification.
3. Implement continuously as the main agent. Choose the detailed order, test real behavior, and keep one compact evidence ledger. Work on independent areas may proceed while a gate awaits review; dependent integration must wait. Use targeted checks during iteration, then a complete candidate verification. Do not repeatedly run unchanged full suites just to produce progress reports.
4. At the selected boundary, checkpoint its source and launch a separate gate reviewer to inspect contracts and run focused adversarial checks. PASS opens dependent work; FAIL requires correction, and INCONCLUSIVE requires missing evidence. Preserve useful executable checks. Later material changes invalidate affected evidence and require focused re-review. Additional reviews require a logged concrete risk, changed contract or unresolved failure requiring independent diagnosis, not elapsed time, cosmetic changes or ordinary progress.
5. Once the primary UI journeys are integrated, before final completion is claimed, checkpoint the UI and launch one independent UI-integration reviewer distinct from the implementer, plan and backend-gate reviewers. Run this once at a useful integrated checkpoint, not on a timer or after every cosmetic change. Review actual same-tab, same-session transitions between accounts/roles, jobs and views with deliberately non-default dates, filters, selections and form values. Check what should reset and what should persist against explicit product policies, including that stale context cannot mislead the next user. Inspect real UI behavior and backend permissions, not just screenshots or passing test summaries. The reviewer returns concrete findings/evidence without editing the application. The main agent corrects findings and adds targeted regression checks; unresolved findings prevent completion. Final validation must independently verify corrections, so a separate correction observer is unnecessary. For tasks without a UI, record the inapplicability rather than inventing a UI.
6. When the result appears complete, run the candidate checks, finish setup/limitations documentation, freeze the delivered source snapshot and launch a fresh final validator, distinct from the implementer and earlier reviewers. Give it the original criteria and evidence index, not an instruction to ratify completion. It must independently exercise the integrated result, including relevant permissions, state/date boundaries, persistence, primary user journeys and required UX/accessibility. In final validation, explicitly exercise transitions between users, roles, jobs and views within the same browser tab and session, without a page reload masking stale state. Set non-default dates, filters, selections and form state first; verify each resets or persists according to the documented policy. Verify UI-review corrections independently. Automated PASS alone is not whole-goal approval. Fix FAIL findings and invalidate affected prior evidence; after relevant changes obtain another fresh final review of the corrected snapshot. INCONCLUSIVE stays unverified.

Do not create a separate observer to verify routine corrections. The implementer runs targeted regression checks; gate re-review is needed only when gate evidence is affected. Final verification remains independent and comprehensive. Never omit a required check or weaken acceptance criteria to meet an efficiency target.
